## 1. Abstract

Alithia-agent expresses a researcher's interests as a directory of Markdown files with YAML frontmatter — one file per knowledge unit. This RFC defines the file format, the provenance split between hand-written and Zotero-synced units, the startup sync contract that converts a Zotero library into the same Markdown format, and the unified-corpus matching rule by which PaperScout ranks ArXiv papers against both interest units and the Zotero corpus with a single embedding pass. It also makes Zotero an optional contributor, honoring the graceful-degradation invariant that [RFC-003-paperscout-workflow](RFC-003-paperscout-workflow.md) §11.2 already requires.

---

## 2. Scope and Non-Goals

### 2.1 Scope

This RFC defines:

* The Markdown + YAML frontmatter format for a research-interests knowledge unit
* The directory layout under `ALITHIA_HOME/research_interests/`
* The `ResearchInterest` data model and its `searchable_text` contract
* The startup Zotero → Markdown sync contract (fetch, write, prune, cache)
* The unified-corpus matching rule used by `PaperReranker`
* The optional-Zotero invariant and the "no knowledge source" fail-fast rule
* The configuration change that deprecates the `research_interests` YAML list

### 2.2 Non-Goals

This RFC does **not** define:

* The ArXiv fetch scope — that remains driven by `paperscout_agent.query` ([RFC-003](RFC-003-paperscout-workflow.md) §8.1). Interests drive **ranking only**.
* The embedding model or algorithm — `all-MiniLM-L6-v2` cosine + time-decay stays as defined in [RFC-003](RFC-003-paperscout-workflow.md) §7.2.
* Storage schema changes — the Zotero cache table and notification tables are unchanged.
* PaperLens integration — interests are a PaperScout concern for now.
* A GUI or interactive editor for interest files.

---

## 3. Background & Motivation

Before this RFC, `research_interests` was a `list[str]` in `~/.alithia/config.yml` that was **declared but never consumed**: it appeared in `config/schema.py` and `config/loader.py` defaults but no node, reranker, prompt, or filter read it. The only relevance signal in PaperScout was the Zotero library corpus, scored via FastEmbed cosine similarity with time-decay weighting. Two problems followed:

1. **Interests carried no weight.** A researcher's stated focus had zero effect on which papers surfaced.
2. **Zotero was a hard gate.** `profile_analysis_node` rejected any run lacking `config.zotero`, even though the schema marked it `Optional`, [RFC-003](RFC-003-paperscout-workflow.md) §11.2 declared *"Zotero unavailable → MUST continue with ArXiv-only"*, and `validate_paperscout_config.py` only warned. Three layers disagreed.

This RFC makes interests the primary, human-editable knowledge source, makes Zotero an optional contributor that is normalized into the same format, and unifies both into one corpus the reranker scores against — thereby making the documented graceful-degradation invariant actually true.

---

## 4. Design Principles

1. **Markdown is the source of truth**: interests are plain `.md` files a researcher can read, write, and version-control. No database, no opaque profile blob.
2. **One file, one embedding**: every knowledge unit (hand-written or Zotero-synced) is a single file that produces exactly one corpus embedding row. Uniform granularity keeps the matcher simple.
3. **Provenance is explicit**: the `source` frontmatter field distinguishes `manual` from `zotero`. The sync step only ever manages `source: zotero` files; hand-written files are never overwritten or deleted.
4. **Zotero is optional**: a run succeeds with interests alone, with Zotero alone, or with both. It fails fast only when neither knowledge source exists.
5. **Unified corpus, single pass**: interests and Zotero papers are combined into one corpus before the existing embedding/time-decay algorithm runs — no second matcher, no separate signal fusion.
6. **Fetch scope unchanged**: interests influence ranking, not which ArXiv categories are queried. This keeps the fetch contract in [RFC-003](RFC-003-paperscout-workflow.md) §8.1 stable.

## 5. Knowledge Base Format

### 5.1 Directory Layout

```
ALITHIA_HOME/research_interests/
├── multimodal-learning.md        # hand-written
├── llm-agents.md                 # hand-written
└── zotero/
    ├── ABC123.md                 # auto-generated by sync
    └── DEF456.md                 # auto-generated by sync
```

* `ALITHIA_HOME` is the existing home directory (default `~/.alithia/`), see [RFC-006](RFC-006-configuration.md) §5.1 and `alithia_agent/__init__.py`.
* Hand-written files live directly under `research_interests/`.
* Zotero-synced files live under `research_interests/zotero/`.
* The loader scans **all** `*.md` recursively, so subdirectories are an organizational concern only.

### 5.2 File Format

Each file is a Markdown document with a YAML frontmatter block delimited by `---`, followed by a free-form Markdown body. The body is the "knowledge text" that gets embedded.

```markdown
---
title: "Multimodal Representation Learning"
source: manual
weight: 1.0
arxiv_categories: [cs.CV, cs.CL]
tags: [vision-language, contrastive]
notes: "Prioritize cross-modal alignment and evaluation benchmarks."
date_added: 2026-06-29
---

## Why I care
Cross-modal alignment is the bottleneck for generalist agents.

## Subtopics
- Contrastive pretraining (CLIP, SigLIP)
- Evaluation benchmarks (VQA, MMMU)
```

### 5.3 Frontmatter Contract

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `title` | `str` | Yes | — | Human-readable unit label. A file missing `title` is skipped with a warning. |
| `source` | `Literal["manual","zotero"]` | No | `manual` | Provenance. Drives which files the sync step may prune. |
| `weight` | `float` | No | `1.0` | Non-negative multiplier on this unit's similarity contribution. |
| `arxiv_categories` | `list[str]` | No | `[]` | Informational only. Does **not** drive ArXiv fetch (Non-Goal §2.2). |
| `tags` | `list[str]` | No | `[]` | Extra keywords appended to the embedded text. |
| `notes` | `str` | No | `""` | Short priority/context note prepended to the embedded text. |
| `date_added` | `date` | No | `None` | Recency key for time-decay. Manual files may omit (treated as oldest). |
| `zotero_item_key` | `str` | Only if `source=zotero` | — | Zotero item key; used by re-sync to prune removed items. |

### 5.4 Embedded Text Contract

The text fed to the embedder for a unit MUST be:

```
<notes> + <markdown body, frontmatter stripped> + " ".join(<tags>)
```

This mirrors the existing `ZoteroPaper.get_searchable_text()` weighting philosophy (title×3, abstract×2, tags×1) in [RFC-008-data-models](RFC-008-data-models.md) §5.3 — title and tags still contribute, but for interest units the body prose is the primary signal.

## 6. Data Model

### 6.1 ResearchInterest

A Pydantic v2 model (`extra="allow"`, per [RFC-008](RFC-008-data-models.md) §11.1 house style for data models) carrying the parsed frontmatter plus the computed embedded text.

```python
class ResearchInterest(BaseModel):
    """One knowledge unit parsed from a research_interests/*.md file."""

    model_config = ConfigDict(extra="allow")

    title: str
    source: Literal["manual", "zotero"] = "manual"
    weight: float = Field(default=1.0, ge=0.0)
    arxiv_categories: list[str] = Field(default_factory=list)
    tags: list[str] = Field(default_factory=list)
    notes: str = ""
    date_added: date | None = None
    zotero_item_key: str | None = None

    # The raw markdown body (frontmatter stripped), set by the loader.
    body: str = ""

    @property
    def display_title(self) -> str:
        return self.title

    def get_searchable_text(self) -> str:
        """Text fed to the embedder: notes + body + tags."""
        parts: list[str] = []
        if self.notes:
            parts.append(self.notes)
        if self.body:
            parts.append(self.body)
        if self.tags:
            parts.append(" ".join(self.tags))
        return " ".join(parts)
```

### 6.2 Module Layout

```
alithia_agent/research_interests/
├── __init__.py        # public API
├── model.py           # ResearchInterest
├── loader.py          # load_research_interests(dir) -> list[ResearchInterest]
└── zotero_sync.py     # sync_zotero_to_markdown(config, dir) -> SyncResult
```

## 7. Loading Contract

### 7.1 `load_research_interests(dir: Path) -> list[ResearchInterest]`

* Recursively glob `*.md` under `dir`.
* For each file: split the leading `---`-delimited block as YAML frontmatter; the remainder is the body.
* Parse frontmatter with `yaml.safe_load`; construct a `ResearchInterest`.
* A file with no frontmatter, malformed YAML, or a missing `title` MUST be skipped with a logged warning, not raise.
* Returns units in a stable order (sorted by relative path) so reranking is deterministic across runs.
* **Pure function**: no network, no side effects, no cache. Trivially unit-testable with a temp directory.

### 7.2 Invariants

* The loader MUST NOT write, delete, or modify any file.
* The loader MUST NOT reach the Zotero API.
* The loader MUST tolerate an empty/missing directory (returns `[]`).

---

## 8. Zotero Sync Contract

### 8.1 When

Sync runs once per PaperScout execution, inside `data_collection_node`, **before** `load_research_interests` is called. It is the step that "downloads the zotero repo as research_interests markdown" so that, combined with the scanned hand-written files, the reranker has a unified knowledge base.

### 8.2 `sync_zotero_to_markdown(config, dir) -> SyncResult`

* If `researcher_profile.zotero` is unset → **no-op**: return `SyncResult(synced=0, pruned=0, skipped=True)`. This is the optional-Zotero path.
* Else fetch the library via `pyzotero`, honoring the existing 24h `paperscout:zotero:{user_id}` SQLite cache ([RFC-003](RFC-003-paperscout-workflow.md) §7.3).
* For each fetched item, write `dir/zotero/<item_key>.md` with:
  * frontmatter `source: zotero`, `zotero_item_key: <key>`, `title`, `tags`, `date_added`
  * body = the item's `abstractNote` (the strongest free-text signal available).
* **Prune**: delete every `zotero/*.md` whose `zotero_item_key` is no longer in the fetched set — so items removed from the library disappear from the knowledge base.
* **Never** touch files outside `zotero/`: hand-written interest files are immutable to the sync.

### 8.3 Optional Dependency

`pyzotero` MUST be imported lazily inside the sync function (and inside the legacy `data_collection_node` zotero branch), not at module top-level. A system without `pyzotero` installed MUST still import `paperscout.nodes` and run PaperScout against hand-written interests.

### 8.4 SyncResult

```python
@dataclass(frozen=True)
class SyncResult:
    synced: int          # files written
    pruned: int          # stale zotero files removed
    skipped: bool        # True when zotero unconfigured or pyzotero missing
    error: str | None    # non-fatal error message, if any
```

Sync errors MUST be non-fatal: a failed sync logs a warning and continues with whatever interest files already exist on disk (the cache, or previously synced files).

## 9. Interests-Only Matching Rule

### 9.1 Unified Corpus Construction

`PaperReranker` scores ArXiv papers against **only** the research-interests knowledge base — `interests: list[ResearchInterest]`. There is **no separate Zotero-paper corpus path**: Zotero items are synced into `zotero/*.md` (§8) and arrive here as `ResearchInterest(source="zotero")` units, indistinguishable from hand-written units for matching purposes. The legacy `corpus: list[ZoteroPaper]` parameter was removed to keep one matching logic and to avoid double-counting.

Before embedding, every interest unit is normalized into a homogeneous corpus row:

| Unit origin | Text source | Weight | Date key |
|-------------|-------------|--------|----------|
| `ResearchInterest` (`source="manual"`) | `interest.get_searchable_text()` | `interest.weight` | `interest.date_added` |
| `ResearchInterest` (`source="zotero"`) | `interest.get_searchable_text()` (body = the Zotero abstract) | `interest.weight` (synced units default to `1.0`) | `interest.date_added` |

Each unit contributes exactly one embedding row. The existing cosine + time-decay algorithm runs unchanged over the unified matrix.

### 9.2 Weighting

* A unit's similarity contribution is multiplied by its `weight` before the time-decay weighted sum.
* Manual units may carry `weight > 1.0` to emphasize stated interests; Zotero-synced units default to `1.0`.
* `weight` is clamped to `ge=0.0` (a weight of `0.0` lets a user "park" a unit without deleting it).

### 9.3 Recency

Time-decay still sorts units newest-first by `date_added`. Manual units without a `date_added` sort to the recency bottom (lowest decay weight), reflecting that undated interests are evergreen rather than recent.

### 9.4 Degradation

* If the corpus is **non-empty** but has no valid text (all units' text < 50 chars) → `score=5.0` fallback with `relevance_factors={"no_corpus_text": 5.0}`.
* If the corpus is **empty** (no interests loaded) → `score=5.0` fallback. This case is reached only when the user has configured nothing; `profile_analysis_node` (§10) fails fast before this point in practice.
* Encoder unavailable → `_fallback_rank()` keyword path, drawing keywords from interest titles and tags.

### 9.5 Observability

`ScoredPaper.relevance_factors` gains:

| Factor | Type | Description |
|--------|------|-------------|
| `interests_count` | `int` | Number of interest units in the corpus (manual + zotero-synced). |
| `interest_weight` | `float` | Max weight among manual (hand-written) units contributing to this paper's score. |

Existing `corpus_similarity`, `corpus_size`, `max_similarity`, `mean_similarity` are preserved.

## 10. Optional-Zotero Invariant

### 10.1 `profile_analysis_node` Rule

The hard Zotero gate is removed. The new validation rule is:

| State | Outcome |
|-------|---------|
| Has interests (≥1 `.md` resolves) and/or has zotero configured | Pass |
| No interests **and** no zotero | Fail fast: *"No knowledge source: add research_interests markdown files or configure zotero"* |

This aligns the runtime with [RFC-006](RFC-006-configuration.md) §4.6 ("fail fast") and makes [RFC-003](RFC-003-paperscout-workflow.md) §11.2 ("Zotero unavailable → MUST continue with ArXiv-only") actually true.

### 10.2 AgentState

`AgentState` carries `research_interests: list[ResearchInterest]` (default `[]`) as the **sole** knowledge-corpus slot. The legacy `zotero_papers` slot was **removed** — Zotero items reach the matcher only as `source="zotero"` `ResearchInterest` units loaded from the synced markdown. (The `paperscout:zotero:{user_id}` SQLite cache remains, as the sync cache, but no longer backs a corpus slot.)

### 10.3 Runtime Config

`PaperScoutRuntimeConfig` gains `research_interests_dir: str | None = None`, set by `build_runtime_config` to `ALITHIA_HOME / "research_interests"`. This transports the resolved path into the graph without re-resolving `ALITHIA_HOME` inside nodes.

## 11. Configuration Changes

### 11.1 Zotero

`researcher_profile.zotero` ([RFC-006](RFC-006-configuration.md) §6.3) is **genuinely optional** at every layer: schema, runtime config, and `profile_analysis_node`. No behavior change for users who already configure it.

### 11.2 Removed `research_interests` List

The `research_interests: list[str]` field was **removed** from `researcher_profile` ([RFC-006](RFC-006-configuration.md) §6.3.1). Interests are read exclusively from the Markdown directory. `ResearcherProfileConfig` uses `extra="allow"`, so a config that still carries a legacy list key loads fine (the key is silently ignored). The `expertise_level` field was removed in the same pass (it was never read at runtime). A migration seeds the legacy list values into Markdown files so no knowledge is lost.

### 11.3 New Path

The interests directory is implicit (`ALITHIA_HOME/research_interests/`); no new config field is required to point at it. `ALITHIA_HOME` already exists ([RFC-006](RFC-006-configuration.md) §5.1).

## 12. Migration

### 12.1 Seed Files

For a user whose legacy list is `[AI, Machine Learning, Computer Vision]`, the migration creates:

```
~/.alithia/research_interests/
├── 01-ai.md
├── 02-machine-learning.md
└── 03-computer-vision.md
```

Each seeded with a `title`, `source: manual`, and a short body explaining the interest so the unit embeds as meaningful text (a bare two-word string embeds poorly).

### 12.2 What Does Not Change

* ArXiv fetch categories, date logic, SMTP/email, exactly-once notification, affiliation extraction, storage schema, CLI, daemon.
* The `ZoteroPaper` model (still a shared data-model contract in [RFC-008](RFC-008-data-models.md) and the shape the sync cache stores) — but it is **no longer a reranker input**; the `zotero_papers` `AgentState` slot was removed.
* The `paperscout:zotero:{user_id}` SQLite cache and `paperscout_zotero_cache` table — retained as the sync cache.
* `pyproject.toml` dependencies (`pyyaml` already present for frontmatter parsing; `pyzotero` stays a core dep, only its import becomes lazy).

## 15. Conclusion

Research interests become a human-editable Markdown knowledge base that is the **sole** input to PaperScout matching. Zotero is normalized into the same Markdown format at startup and arrives at the matcher as `source="zotero"` `ResearchInterest` units — there is no separate Zotero-paper corpus path. Zotero becomes optional, making the documented graceful-degradation invariant true for the first time, and the matcher keeps exactly one matching logic.

> **Interests are Markdown files; Zotero is one optional contributor among them; one corpus, one embedding pass, one matching logic.**
