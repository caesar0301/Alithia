## 1. Abstract

PaperScout is the paper discovery agent within the Alithia ecosystem, responsible for automated arXiv paper collection, relevance assessment, and user notification. This RFC defines the architecture of the PaperScout agent, including its components, data flows, storage integration, and operational guarantees. PaperScout runs scheduled queries, assesses paper relevance using LLM-based analysis, and delivers personalized paper recommendations via email while maintaining persistent state to ensure exactly-once notification semantics.

---

## 2. Scope and Non-Goals

### 2.1 Scope

This RFC defines:

* The architecture and components of the PaperScout agent
* Data flow for paper discovery, assessment, and notification
* Storage integration for persistent state management
* Asynchronous profile synchronization from Zotero
* Gap scanning service for missed recommendation slots
* Abstract schemas for papers, queries, and notifications
* Invariants specific to PaperScout operations

### 2.2 Non-Goals

This RFC does **not** define:

* Concrete API signatures or Python interfaces (see Implementation Interface Design specs)
* LLM prompt engineering details
* Email template formatting
* Deployment configuration or GitHub Actions workflow syntax

## 3. Background & Motivation

Researchers need to stay current with the latest publications in their fields, but the volume of papers on arXiv makes manual monitoring impractical. PaperScout automates this process by:

1. **Scheduled Discovery**: Running daily queries against arXiv based on user-defined criteria
2. **Intelligent Assessment**: Using LLM capabilities to evaluate paper relevance to the user's research profile
3. **Reliable Notification**: Delivering exactly-once email notifications for new relevant papers
4. **Gap Filling**: Detecting and recovering from missed execution slots

PaperScout integrates with the Research Profile for personalization and the Storage Backend for state persistence, enabling continuous operation across sessions and handling connectivity issues gracefully.

## 5. Components

### 5.1 Query Scheduler

**Responsibility**: Manage and execute scheduled paper queries.

The Query Scheduler maintains the list of daily queries configured by the user and triggers their execution at the appropriate times. Each query specifies:
- ArXiv search criteria (categories, keywords, date range)
- Schedule (daily, specific time)
- Notification preferences

**Key Behaviors**:
- Executes queries on schedule
- Handles execution failures with retry logic
- Records execution history in Storage
- Supports manual trigger for testing

### 5.2 ArXiv Fetcher

**Responsibility**: Retrieve papers from ArXiv based on query criteria.

The ArXiv Fetcher interacts with the ArXiv API and web scraping capabilities to collect papers matching the query parameters.

**Key Behaviors**:
- Queries ArXiv API for paper metadata
- Falls back to web scraping when API is unavailable
- Respects ArXiv rate limits
- Parses paper metadata (title, authors, abstract, categories)
- Handles ArXiv indexing delays gracefully

### 5.3 Profile Syncer

**Responsibility**: Synchronize user profile data from connected services.

The Profile Syncer runs asynchronously to keep the Research Profile enriched with data from external services.

**Key Behaviors**:
- Syncs Zotero library for reference context
- Extracts research interests from paper library
- Updates profile embedding vectors for similarity matching
- Runs in background without blocking paper discovery

### 5.4 Relevance Assessor

**Responsibility**: Evaluate paper relevance to the user's research profile.

The Relevance Assessor uses LLM capabilities to score papers against the user's interests and expertise.

**Key Behaviors**:
- Computes relevance score using LLM analysis
- Considers user's research interests and expertise
- Uses Zotero library for context enrichment
- Produces structured assessment with reasoning

### 5.5 Paper Reranker

**Responsibility**: Reorder papers by relevance and diversity.

The Paper Reranker organizes assessed papers into a ranked list optimized for the user.

**Key Behaviors**:
- Sorts papers by relevance score
- Applies diversity constraints to avoid topic clustering
- Limits output to configurable maximum
- Generates summary explanations for ranking

### 5.6 Paper Processor

**Responsibility**: Orchestrate the paper processing pipeline.

The Paper Processor coordinates the fetch-assess-rerank pipeline for a single query execution.

**Key Behaviors**:
- Invokes ArXiv Fetcher with query parameters
- Passes papers to Relevance Assessor
- Coordinates with Paper Reranker
- Persists results to Storage

### 5.7 Email Notifier

**Responsibility**: Deliver paper recommendations via email.

The Email Notifier formats and sends email notifications for processed papers.

**Key Behaviors**:
- Formats papers into email template
- Sends via configured SMTP (default Gmail)
- Records notification in Storage
- Implements exactly-once semantics via deduplication

### 5.8 Storage Gateway

**Responsibility**: Abstract storage operations for PaperScout.

The Storage Gateway provides a unified interface to the Storage Backend, handling Supabase/SQLite fallback logic.

**Key Behaviors**:
- Reads and writes paper records
- Manages query execution history
- Stores notification records
- Handles backend failover transparently

### 5.9 Gap Scanner

**Responsibility**: Detect and fill missed recommendation slots.

The Gap Scanner is a background service that identifies days without paper recommendations and triggers re-execution.

**Key Behaviors**:
- Scans for missing recommendation slots
- Triggers Query Scheduler for gap periods
- Limits retry attempts to prevent spam
- Logs gap recovery actions

### 6.2 Flow Description

1. **Query Trigger**: Query Scheduler initiates daily run for each configured query
2. **Profile Loading**: Load user's research profile including interests and Zotero context
3. **Gap Detection**: Gap Scanner checks for missing slots and triggers catch-up if needed
4. **Paper Fetching**: ArXiv Fetcher retrieves papers matching query criteria
5. **Deduplication**: Filter out papers already processed (from Storage)
6. **Relevance Assessment**: LLM-based evaluation against user profile
7. **Ranking**: Rerank by relevance and diversity
8. **Persistence**: Save processed papers to Storage
9. **Notification Check**: Verify no previous notification for this query/date
10. **Email Delivery**: Format and send notification
11. **Record Keeping**: Store notification record for deduplication

## 7. Invariants and Constraints

### 7.1 Architectural Invariants

| Invariant | Meaning | Consequence of Violation |
|-----------|---------|-------------------------|
| **PS-001**: Exactly-once notification | Each query execution results in at most one email | Duplicate notifications annoy users and reduce trust |
| **PS-002**: Gap detection bounded | Gap Scanner only fills gaps within configurable window | Prevents spam from long-ago gaps |
| **PS-003**: Storage-first persistence | All state changes are persisted before notification | Ensures recoverability |
| **PS-004**: Graceful API degradation | ArXiv API failure triggers web scraping fallback | Maintains availability |
| **PS-005**: Profile isolation | PaperScout reads profile but never modifies core fields | Preserves profile integrity |

### 7.2 Dependency Constraints

| Constraint | Rule |
|------------|------|
| Storage Backend | MUST be available (Supabase or SQLite) |
| LLM API | MUST be configured for relevance assessment |
| Email SMTP | SHOULD be configured for notifications (optional) |
| Zotero API | MAY be configured for profile enrichment (optional) |

### 7.3 Operational Constraints

| Constraint | Description |
|------------|-------------|
| Rate Limiting | ArXiv API: 1 request per 3 seconds |
| Batch Size | Maximum 100 papers per query |
| Assessment Timeout | LLM assessment: 30 seconds per paper |
| Email Size | Maximum 50 papers per email |

## 8. Abstract Schemas

### 8.1 Paper Record

Represents a discovered and assessed paper.

| Field | Type | Description |
|-------|------|-------------|
| `arxiv_id` | String | Unique ArXiv identifier |
| `title` | String | Paper title |
| `authors` | List[String] | Author names |
| `abstract` | String | Paper abstract |
| `categories` | List[String] | ArXiv categories |
| `published_date` | Date | Publication date on ArXiv |
| `pdf_url` | URL | Link to PDF |
| `abs_url` | URL | Link to abstract page |
| `relevance_score` | Float | 0.0-1.0 relevance to user profile |
| `relevance_reason` | String | LLM-generated explanation |
| `assessed_at` | Timestamp | When relevance was assessed |
| `query_id` | String | ID of query that discovered this paper |

### 8.2 Query Configuration

Represents a user's paper query.

| Field | Type | Description |
|-------|------|-------------|
| `query_id` | String | Unique identifier |
| `user_id` | String | Owner's user ID |
| `name` | String | Human-readable query name |
| `categories` | List[String] | ArXiv categories to search |
| `keywords` | List[String] | Keywords to match |
| `date_range` | Enum | `last_day`, `last_week`, `custom` |
| `schedule` | Cron | Execution schedule |
| `max_papers` | Integer | Maximum papers per run |
| `min_relevance` | Float | Minimum relevance threshold |
| `email_enabled` | Boolean | Whether to send notifications |
| `created_at` | Timestamp | Query creation time |
| `last_run` | Timestamp | Last execution time |

### 8.3 Notification Record

Tracks sent notifications to prevent duplicates.

| Field | Type | Description |
|-------|------|-------------|
| `notification_id` | String | Unique identifier |
| `query_id` | String | Associated query |
| `user_id` | String | Recipient user ID |
| `date` | Date | Notification date |
| `paper_count` | Integer | Number of papers included |
| `sent_at` | Timestamp | When notification was sent |
| `status` | Enum | `pending`, `sent`, `failed` |
| `error_message` | String | Error if failed |

### 8.4 Execution History

Records query execution for gap detection.

| Field | Type | Description |
|-------|------|-------------|
| `execution_id` | String | Unique identifier |
| `query_id` | String | Associated query |
| `date` | Date | Execution date |
| `status` | Enum | `success`, `partial`, `failed` |
| `papers_found` | Integer | Number of papers discovered |
| `papers_relevant` | Integer | Papers passing relevance threshold |
| `notification_sent` | Boolean | Whether email was sent |
| `started_at` | Timestamp | Execution start time |
| `completed_at` | Timestamp | Execution end time |
| `error_message` | String | Error if failed |

## 10. Open Questions

1. **Multi-User Scaling**: How should the Query Scheduler handle multiple users? Should queries be user-isolated or shared?

2. **Assessment Caching**: Should paper assessments be cached globally? If two users have similar profiles, can assessments be reused?

3. **Notification Preferences**: Should users be able to configure digest frequency (weekly instead of daily)?

4. **Query Templates**: Should PaperScout provide pre-configured query templates for common research areas?

5. **Feedback Loop**: How should user feedback on recommendations (e.g., "not relevant") be incorporated into future assessments?

---

## 11. Conclusion

PaperScout automates the paper discovery workflow through a well-defined architecture of cooperating components. The agent adheres to Alithia's core principles of researcher-centricity, asynchronous operation, and graceful degradation. By persisting all state in the Storage Backend and implementing exactly-once notification semantics, PaperScout provides reliable, personalized paper recommendations that help researchers stay current with minimal manual effort.

The Gap Scanner ensures that no recommendation slot is missed due to system downtime, while the Profile Syncer continuously enriches the user's research context. Together, these components provide a robust foundation for automated academic discovery.
