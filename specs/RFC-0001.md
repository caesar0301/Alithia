## 1. Abstract

Alithia is an AI-powered research assistant that connects researcher profiles with academic resources and cloud infrastructure to automate and enhance the research workflow. This RFC defines the foundational design philosophy, core abstractions, system-wide principles, and the conceptual model for the Alithia agent ecosystem. It establishes the vision of Alithia as a multi-agent platform where specialized agents (PaperScout, PaperLens) collaborate to serve researchers' needs for paper discovery, deep reading, and interest-driven exploration.

## 2. Scope and Non-Goals

### 2.1 Scope

This RFC defines:

* The overall vision and mission of Alithia as a research assistant platform
* Core design principles that guide all architectural decisions

This RFC does **not** define:

## 3. Background & Motivation

Time is one of the most valuable resources for a human researcher, best spent on thinking, exploring, and creating in the world of ideas. Modern researchers face an overwhelming volume of academic publications, making it challenging to stay current with relevant developments in their fields.

Alithia addresses this challenge by:

1. **Bridging personal context with public knowledge**: Connecting a researcher's profile (interests, expertise, library) with public academic resources (arXiv, Google Scholar)
2. **Automating routine discovery**: Freeing researchers from manual paper hunting through intelligent agents
3. **Enabling deep exploration**: Supporting in-depth paper analysis and topic investigation
4. **Providing persistent memory**: Maintaining state across sessions to build institutional knowledge

The multi-agent architecture allows for specialized, focused capabilities while maintaining a cohesive user experience through shared profiles and storage.

## 4. Design Principles

### 4.1 Researcher-Centricity

**Principle**: Every feature, agent, and interaction MUST be designed to serve the researcher's goals.

- Agents act as extensions of the researcher's capabilities
- User preferences and profile data drive personalization
- The system augments human intelligence rather than replacing it

### 4.2 Profile as the Source of Truth

**Principle**: The Research Profile is the single source of truth for personalization.

- All agents derive their behavior from the same profile
- Profile updates propagate to all dependent components
- Connected services enrich the profile asynchronously

### 4.3 Asynchronous by Default

**Principle**: Long-running operations MUST be asynchronous with proper state management.

- Paper discovery and analysis run independently of user sessions
- Profile synchronization happens in the background
- Results are persisted and available on demand

### 4.4 Graceful Degradation

**Principle**: The system MUST function with reduced capabilities when external services are unavailable.

- Storage falls back from Supabase to SQLite when cloud is unavailable
- Agents continue with cached data when APIs are unreachable
- User is informed of degraded mode without blocking operations

### 4.5 Extensibility Through Agents

**Principle**: New capabilities are added as new agents, not by expanding existing ones.

- Each agent has a focused, well-defined responsibility
- Agents communicate through shared storage and profile
- New agents integrate without modifying existing ones

## 5. Conceptual Model

### 5.1 Core Abstractions

#### Research Profile

The Research Profile represents the researcher's identity within Alithia. It contains:

- **Basic Information**: Research interests, expertise areas, preferred language
- **Connected Services**: External integrations (LLM, Zotero, Email, GitHub, Google Scholar)
- **Gems**: Captured research digests, ideas, and notes

The profile is the central configuration that drives all agent behaviors.

#### Connected Service

A Connected Service is an external integration that enriches the research experience:

| Service Type | Purpose |
|--------------|---------|
| LLM | Provides AI capabilities for analysis, summarization, and assessment |
| Zotero | Personal paper library for reference and context |
| Email | Notification delivery channel |
| GitHub | Code and project context |
| Google Scholar | Publication history and citations |

Connected Services are configured by the user and accessed asynchronously by agents.

#### Agent

An Agent is an autonomous component with a specific research-related capability:

- **PaperScout**: Discovers and recommends papers from arXiv
- **PaperLens**: Reads papers and performs deep topic research
- **Dashboard**: Web-based interface that unifies agent capabilities with task monitoring, profile management, paper trend visualization, and AI-assisted research

Agents operate independently but share access to the Research Profile and Storage.

#### Gem

A Gem is a captured piece of research knowledge:

- Research digest summaries
- Interesting paper notes
- Exploration insights
- Idea fragments

Gems are created by agents or users and stored for future reference.

#### Storage Backend

The Storage Backend provides persistent state:

- User profiles and preferences
- Paper metadata and assessments
- Notification history
- Query logs

Supports Supabase (cloud) with SQLite fallback for offline/degraded mode.

## 6. Taxonomy

### 6.1 Core Concepts

| Term | Definition |
|------|------------|
| **Research Profile** | User's research identity including interests, expertise, connected services, and gems |
| **Connected Service** | External service integration (LLM, Zotero, Email, GitHub, Google Scholar, X/Twitter) |
| **Gem** | Captured research digest, idea, or note stored in the user's profile |
| **Research Assistant** | The overarching system that orchestrates agents to serve researcher needs |

### 6.2 Agent Types

| Term | Definition |
|------|------------|
| **PaperScout** | Agent responsible for automated paper discovery from ArXiv and user notification |
| **PaperLens** | Agent that reads papers and performs deep research about related topics |
| **Dashboard** | Web-based interface providing task monitoring, profile management, paper trend visualization, and AI-integrated research |

### 6.3 PaperScout Domain

| Term | Definition |
|------|------------|
| **Paper Query** | User-defined search criteria including keywords, categories, and date range |
| **Daily Query** | Paper query scheduled for automatic daily execution |
| **Paper Relevance Assessment** | LLM-based evaluation of paper relevance to user's research profile |
| **Gap Scanner** | Service that detects and fills missing daily paper recommendations |
| **Recommendation Slot** | A single day's worth of paper recommendations for a query |

### 6.4 PaperLens Domain

| Term | Definition |
|------|------------|
| **Paper OCR** | PDF parsing and content extraction using Docling or similar tools |
| **Deep Research** | Extended investigation into paper-related topics using LLM capabilities |
| **Query History** | Persistent record of user interactions and research queries |

### 6.5 Dashboard Domain

| Term | Definition |
|------|------------|
| **Background Task** | A trackable unit of work dispatched from the Dashboard to an agent or service |
| **Paper Trend** | Calendar-based visualization of daily paper discovery results from PaperScout |
| **AI Agent Button** | Persistent UI element that provides contextual AI assistance on any Dashboard page |
| **Agent Dispatcher** | Service that routes Dashboard user actions to the correct agent invocation |

### 6.6 Storage Domain

| Term | Definition |
|------|------------|
| **Storage Backend** | Persistent state storage system (Supabase or SQLite fallback) |
| **User Profile Sync** | Asynchronous synchronization of user data from external services |
| **Paper Record** | Persisted metadata and assessment for a discovered paper |

## 7. Invariants

System-wide invariants that all implementations MUST respect:

### 7.1 Profile Consistency

1. **I-001**: All agents MUST read from the same Research Profile
2. **I-002**: Profile updates MUST be atomic and versioned
3. **I-003**: Connected Service credentials MUST be encrypted at rest

### 7.2 Storage Reliability

1. **I-004**: Every write operation MUST succeed to at least one storage backend
2. **I-005**: SQLite fallback MUST activate automatically when Supabase is unavailable
3. **I-006**: Data written to SQLite MUST be synchronizable to Supabase when connectivity is restored

### 7.3 Agent Independence

1. **I-007**: Agents MUST operate independently without direct inter-agent communication
2. **I-008**: Agent failures MUST NOT cascade to other agents
3. **I-009**: Each agent MUST be restartable from persisted state

### 7.4 Notification Guarantees

1. **I-010**: Each daily query MUST result in at most one email notification
2. **I-011**: Notification history MUST be persisted to prevent duplicates
3. **I-012**: Failed notifications MUST be retried with exponential backoff

## 9. Open Questions

1. **Multi-user Support**: How should the system handle multiple researchers sharing the same Alithia instance? This is deferred to a future RFC.

2. **Agent Communication**: Should agents be able to communicate directly in the future, or should all coordination happen through shared storage? Current design prohibits direct communication.

3. **Gem Evolution**: How should Gems be versioned and evolved over time? What's the lifecycle of a Gem?

4. **Offline Mode Semantics**: What are the exact semantics of offline operation? What features are unavailable, and how is the user notified?

---

## 10. Conclusion

Alithia represents a new paradigm in research assistance: a multi-agent platform that bridges personal research context with the vast landscape of academic knowledge. By adhering to the principles of researcher-centricity, profile-driven personalization, asynchronous operation, graceful degradation, and agent extensibility, Alithia provides a robust foundation for automated paper discovery and deep research exploration.

The conceptual model establishes clear abstractions (Research Profile, Connected Services, Agents, Gems, Storage) and their relationships, while the invariants ensure system reliability and user trust. Future RFCs will build upon this foundation to define the architecture of individual agents and their implementations.

> **Alithia: Your powerful research companion, bridging your profile with the world of academic knowledge.**
