## 1. Abstract

PaperLens is the deep reading and research agent within the Alithia ecosystem, responsible for paper content extraction, analysis, and extended topic exploration. This RFC defines the architecture of the PaperLens agent, including its components for PDF processing, LLM-powered analysis, query management, and interaction history. PaperLens enables researchers to engage deeply with papers through structured analysis, Q&A, and interest-driven research trails.

---

## 2. Scope and Non-Goals

### 2.1 Scope

This RFC defines:

* The architecture and components of the PaperLens agent
* Data flow for paper processing, analysis, and research exploration
* PDF content extraction using Docling or similar OCR tools
* LLM integration for paper analysis and Q&A
* Query history and session management
* Abstract schemas for papers, queries, and research sessions
* Invariants specific to PaperLens operations

### 2.2 Non-Goals

This RFC does **not** define:

* Concrete API signatures or Python interfaces (see Implementation Interface Design specs)
* LLM prompt engineering details for analysis
* Specific paper analysis algorithms or heuristics
* UI/UX for paper interaction (web interface, CLI, etc.)

---

## 3. Background & Motivation

Reading and understanding academic papers is a time-intensive activity that can be enhanced through AI assistance. PaperLens addresses this by:

1. **Content Extraction**: Converting PDF papers into structured, searchable content
2. **Intelligent Analysis**: Using LLM capabilities to summarize, explain, and contextualize papers
3. **Interactive Q&A**: Enabling natural language queries about paper content
4. **Research Trails**: Supporting extended exploration of related topics and papers

PaperLens complements PaperScout: while PaperScout discovers papers, PaperLens helps researchers understand them deeply. Both agents share the Research Profile and Storage Backend but operate independently.

## 5. Components

### 5.1 Session Manager

**Responsibility**: Manage user interaction sessions with papers.

The Session Manager maintains the state of a user's research session, including the current paper, conversation history, and active research trails.

**Key Behaviors**:
- Creates and persists sessions
- Tracks session state (active paper, current topic)
- Maintains conversation history
- Links sessions to Research Profile

### 5.2 Query Processor

**Responsibility**: Parse and route user queries to appropriate handlers.

The Query Processor interprets natural language queries and determines the appropriate analysis action.

**Key Behaviors**:
- Parses natural language queries
- Classifies query type (summary, explanation, comparison, exploration)
- Routes to appropriate analyzer
- Maintains query context

### 5.3 Response Formatter

**Responsibility**: Format analysis results for user presentation.

The Response Formatter structures LLM outputs into readable, well-organized responses.

**Key Behaviors**:
- Formats analysis results with citations
- Generates structured summaries
- Includes paper references and links
- Supports multiple output formats

### 5.4 Paper OCR

**Responsibility**: Extract structured content from PDF papers.

The Paper OCR component uses Docling or similar tools to convert PDFs into structured, machine-readable content.

**Key Behaviors**:
- Extracts text, tables, and figures from PDFs
- Preserves document structure (sections, references)
- Handles various PDF formats and quality levels
- Caches extracted content for performance

### 5.5 Content Chunker

**Responsibility**: Split paper content into processable chunks.

The Content Chunker divides long papers into manageable segments for LLM processing.

**Key Behaviors**:
- Respects section boundaries
- Maintains context across chunks
- Generates chunk embeddings for retrieval
- Handles tables and figures appropriately

### 5.6 Context Builder

**Responsibility**: Assemble relevant context for LLM queries.

The Context Builder gathers paper content, user profile, and conversation history to construct rich context for analysis.

**Key Behaviors**:
- Retrieves relevant chunks via embedding search
- Incorporates user's research interests
- Includes conversation history
- Manages context window limits

### 5.7 Paper Analyzer

**Responsibility**: Perform LLM-powered paper analysis.

The Paper Analyzer executes various analysis tasks on paper content.

**Key Behaviors**:
- Generates paper summaries
- Extracts key contributions and methodology
- Identifies limitations and future work
- Explains technical concepts
- Answers specific questions about the paper

### 5.8 Topic Explorer

**Responsibility**: Discover and explore related topics and papers.

The Topic Explorer extends analysis beyond the current paper to related concepts and works.

**Key Behaviors**:
- Identifies related topics and concepts
- Suggests related papers from the user's library
- Generates research trails (topic → related topics → further exploration)
- Integrates with PaperScout-discovered papers

### 5.9 Research Synthesizer

**Responsibility**: Combine insights across multiple papers and sessions.

The Research Synthesizer creates higher-level insights from accumulated research.

**Key Behaviors**:
- Synthesizes findings across papers
- Identifies themes and contradictions
- Generates literature review drafts
- Creates Gems (research digests)

### 5.10 Profile Gateway

**Responsibility**: Read from Research Profile for context.

The Profile Gateway provides read-only access to user profile data.

**Key Behaviors**:
- Retrieves user's research interests
- Accesses Zotero library for context
- Reads saved Gems for reference
- Never modifies profile (Gem creation goes through Storage)

### 5.11 Storage Gateway

**Responsibility**: Persist PaperLens data to Storage Backend.

The Storage Gateway handles all persistence operations for PaperLens.

**Key Behaviors**:
- Stores extracted paper content
- Saves query history
- Persists research sessions
- Creates Gems

### 5.12 LLM Client

**Responsibility**: Interface with LLM API for analysis.

The LLM Client manages communication with the configured LLM provider.

**Key Behaviors**:
- Sends prompts with context
- Handles rate limiting and retries
- Manages token budgets
- Supports multiple LLM providers (OpenAI-compatible)

### 6.3 Flow Description

**Paper Analysis Flow**:

1. **Session Start**: User initiates a research session
2. **Paper Selection**: User selects a paper to analyze
3. **Content Extraction**: Paper OCR extracts structured content (cached if available)
4. **Content Chunking**: Long papers are divided into processable segments
5. **Query Processing**: User submits a natural language query
6. **Context Building**: Relevant chunks and profile data are assembled
7. **LLM Analysis**: Paper Analyzer processes the query with context
8. **Response Formatting**: Results are formatted with citations
9. **History Persistence**: Query and response are saved for future reference

**Research Exploration Flow**:

1. **Exploration Request**: User asks to explore related topics
2. **Topic Extraction**: Topic Explorer identifies key concepts
3. **Related Content**: Search in paper content and Zotero library
4. **Trail Generation**: Create a research trail of related topics
5. **Synthesis**: Research Synthesizer creates comprehensive insights
6. **Gem Creation**: Valuable insights are saved as Gems

## 7. Invariants and Constraints

### 7.1 Architectural Invariants

| Invariant | Meaning | Consequence of Violation |
|-----------|---------|-------------------------|
| **PL-001**: Read-only Profile Access | PaperLens reads profile but never modifies core fields | Preserves profile integrity for other agents |
| **PL-002**: Content Caching | Extracted content MUST be cached | Avoids re-processing expensive OCR operations |
| **PL-003**: Session Isolation | Each session operates on one paper at a time | Prevents context confusion |
| **PL-004**: Token Budget Management | LLM context MUST respect token limits | Prevents API errors and cost overruns |
| **PL-005**: Query Persistence | All queries and responses MUST be persisted | Enables history and learning |

### 7.2 Dependency Constraints

| Constraint | Rule |
|------------|------|
| Storage Backend | MUST be available for session persistence |
| LLM API | MUST be configured for analysis |
| PDF Processing | Docling or equivalent MUST be available |
| Zotero API | MAY be configured for library context (optional) |

### 7.3 Operational Constraints

| Constraint | Description |
|------------|-------------|
| PDF Size | Maximum 100 pages per paper |
| Chunk Size | 2000-4000 tokens per chunk |
| Context Window | Maximum 128K tokens for context |
| Response Timeout | 60 seconds per LLM call |
| Session Duration | Sessions expire after 24 hours of inactivity |

## 8. Abstract Schemas

### 8.1 Paper Content

Represents extracted and processed paper content.

| Field | Type | Description |
|-------|------|-------------|
| `paper_id` | String | Unique identifier (ArXiv ID or internal) |
| `title` | String | Paper title |
| `source_url` | URL | Original PDF URL |
| `extracted_at` | Timestamp | When content was extracted |
| `sections` | List[Section] | Structured paper sections |
| `references` | List[Reference] | Bibliography entries |
| `figures` | List[Figure] | Extracted figures |
| `tables` | List[Table] | Extracted tables |
| `full_text` | String | Complete text for search |
| `chunk_embeddings` | List[Vector] | Embedding vectors for chunks |

### 8.2 Section

Represents a paper section.

| Field | Type | Description |
|-------|------|-------------|
| `section_id` | String | Unique identifier |
| `title` | String | Section heading |
| `level` | Integer | Heading level (1, 2, 3...) |
| `content` | String | Section text |
| `start_page` | Integer | Starting page number |
| `end_page` | Integer | Ending page number |

### 8.3 Research Session

Represents a user's interaction session with a paper.

| Field | Type | Description |
|-------|------|-------------|
| `session_id` | String | Unique identifier |
| `user_id` | String | Owner's user ID |
| `paper_id` | String | Current paper being analyzed |
| `started_at` | Timestamp | Session start time |
| `last_activity` | Timestamp | Last interaction time |
| `status` | Enum | `active`, `expired`, `closed` |
| `context` | JSON | Session state and context |

### 8.4 Query History

Records user queries and responses.

| Field | Type | Description |
|-------|------|-------------|
| `query_id` | String | Unique identifier |
| `session_id` | String | Associated session |
| `user_id` | String | User who asked |
| `paper_id` | String | Paper being queried |
| `query_text` | String | User's natural language query |
| `query_type` | Enum | `summary`, `explanation`, `comparison`, `exploration`, `other` |
| `response_text` | String | LLM-generated response |
| `context_used` | List[String] | IDs of chunks used for context |
| `created_at` | Timestamp | Query time |
| `feedback` | Enum | `helpful`, `not_helpful`, `none` |

### 8.5 Research Trail

Records exploration paths through topics.

| Field | Type | Description |
|-------|------|-------------|
| `trail_id` | String | Unique identifier |
| `session_id` | String | Associated session |
| `starting_topic` | String | Initial topic from paper |
| `topics` | List[Topic] | Explored topics |
| `related_papers` | List[String] | IDs of related papers found |
| `created_at` | Timestamp | Trail creation time |

### 8.6 Topic

Represents a research topic in a trail.

| Field | Type | Description |
|-------|------|-------------|
| `topic_id` | String | Unique identifier |
| `name` | String | Topic name/label |
| `description` | String | Brief description |
| `source` | Enum | `paper`, `user_query`, `exploration` |
| `relevance` | Float | Relevance to session (0.0-1.0) |

## 10. Open Questions

1. **Multi-Paper Sessions**: Should sessions support multiple papers simultaneously? How would context be managed?

2. **Collaborative Research**: How could PaperLens support collaborative research sessions between multiple users?

3. **Learning from Feedback**: How should user feedback on query responses be used to improve future analyses?

4. **Paper Versioning**: How should PaperLens handle multiple versions of the same paper (e.g., ArXiv v1, v2, v3)?

5. **External Knowledge**: Should PaperLens integrate with external knowledge bases (Wikipedia, Semantic Scholar)? How?

6. **Citation Graph**: Should PaperLens build and traverse citation graphs for exploration?

## 11. Conclusion

PaperLens provides the deep reading and research capabilities that complement PaperScout's discovery function. Through a well-architected set of components, PaperLens enables researchers to engage deeply with papers through intelligent analysis, interactive Q&A, and extended topic exploration.

The architecture emphasizes session management, context building, and LLM integration while maintaining clear separation of concerns. By persisting all interactions and creating Gems from valuable insights, PaperLens builds a knowledge base that grows with the researcher's engagement.

Together with PaperScout, PaperLens forms the core of Alithia's research assistance capabilities: discovery and understanding, automated and guided, all centered on the researcher's profile and preferences.

> **PaperLens: Your intelligent reading companion, helping you understand and explore research deeply.**
