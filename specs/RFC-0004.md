## 1. Abstract

The Alithia Dashboard is a web-based user interface that unifies all Alithia capabilities into a cohesive, interactive experience. It provides background task monitoring, user profile and connected services management, a Paper Trend calendar view built on PaperScout data, and an AI Agent integration layer that lets users trigger contextual chat or deep research from any UI element. This RFC defines the architecture of the Dashboard, its pages, data flows, real-time communication model, and integration with existing agents and storage.

---

## 2. Scope and Non-Goals

### 2.1 Scope

This RFC defines:

* The architecture and components of the Alithia Dashboard
* Background Task abstraction for progress monitoring and logging
* User Profile page with Connected Service status and sync summaries
* Paper Trend page with calendar-based discovery visualization
* AI Agent Button integration for contextual chat and deep research
* Data flow between Dashboard, Storage Backend, and agent services
* Abstract schemas for tasks, dashboard state, and UI interactions
* Invariants specific to Dashboard operations

### 2.2 Non-Goals

This RFC does **not** define:

* Concrete UI component library or CSS framework selection
* Specific frontend build tooling or bundler configuration
* LLM prompt engineering for AI Agent interactions
* Mobile-specific layout or responsive design breakpoints
* User authentication and multi-user session management (deferred to future RFC)

## 3. Background & Motivation

Alithia's agents (PaperScout, PaperLens) currently operate through CLI commands and scheduled GitHub Actions. While effective for automation, this interface lacks:

1. **Visibility**: No way to see what the system is doing, what tasks are running, or what failed
2. **Discoverability**: Paper recommendations are delivered via email only; there's no browsable history
3. **Interactivity**: Users cannot trigger ad-hoc research or chat about papers without leaving the terminal
4. **Configuration**: Service connections and profile settings require editing JSON files

The Dashboard addresses all four gaps by providing a web interface that surfaces storage data, monitors background tasks, and integrates AI capabilities directly into the UI.

---

## 4. Design Principles

### 4.1 Storage as the Single Source of Truth

**Principle**: The Dashboard reads from and writes to the same Storage Backend that agents use. It MUST NOT maintain a separate data store.

All data displayed in the Dashboard — assessed papers, sync status, notification records — comes from the existing Supabase/SQLite storage. The Dashboard is a view layer over shared state.

### 4.2 Agent Orchestration, Not Replacement

**Principle**: The Dashboard orchestrates agents; it does NOT re-implement agent logic.

When a user triggers paper discovery or gap filling from the Dashboard, the request is dispatched to the actual PaperScout agent, not to Dashboard-internal code.

### 4.3 Progressive Enhancement

**Principle**: Core features MUST work without real-time connections. Real-time updates are enhancements.

The Dashboard loads data from storage on page load. WebSocket or polling connections provide live updates for running tasks, but the UI MUST be functional without them.

### 4.4 AI-Everywhere Integration

**Principle**: The AI Agent Button SHOULD be accessible from any page and context-aware of the current UI focus.

Users can select UI targets (a paper, a date range, a sync status) and invoke AI assistance with that context pre-populated.

## 6. Components

### 6.1 Overview Page (Background Tasks)

**Responsibility**: Display system status, running tasks, recent activity, and task logs.

The Overview Page is the Dashboard landing page. It provides at-a-glance visibility into what the system is doing.

**Key Behaviors**:
- Displays a list of Background Tasks with status (running, completed, failed, queued)
- Shows real-time progress for running tasks (e.g., "Fetching ArXiv papers: 120/500")
- Provides expandable task detail with structured logs
- Allows users to manually trigger tasks (sync, paper discovery, gap fill)
- Shows system health summary (storage connectivity, last sync time, last discovery time)

### 6.2 Profile & Configuration Page

**Responsibility**: Manage user profile and Connected Service configurations.

The Profile Page lets users view and edit their Research Profile and manage Connected Service credentials and status.

**Key Behaviors**:
- Displays Research Profile fields (interests, expertise, language)
- Shows Connected Service cards with:
  - Connection status (connected, disconnected, error)
  - Last sync timestamp
  - Sync summary (e.g., "Zotero: 342 papers synced")
  - Service-specific details (Zotero collection stats, Scholar h-index)
- Allows editing profile fields and service credentials
- Triggers manual sync for individual services
- Displays sync history with success/failure indicators

### 6.3 Paper Trend Page (Calendar)

**Responsibility**: Visualize paper discovery history as an interactive calendar.

The Paper Trend Page is built on PaperScout's `assessed_papers` and `notification_records` data. It provides a calendar-based view of daily paper recommendations.

**Key Behaviors**:
- Displays a month calendar with daily paper counts as heatmap cells
- Each cell shows: paper count, notification status (sent, failed, missing)
- Clicking a calendar day opens a detail panel with the full list of assessed papers for that date
- Paper list shows: title, authors, relevance score, TL;DR, PDF link, code link (same content as email)
- Supports filtering by ArXiv category, relevance threshold, date range
- Shows summary statistics: total papers assessed, average relevance, top categories
- Allows triggering gap fill for missing dates directly from the calendar

### 6.4 AI Agent Button

**Responsibility**: Provide contextual AI assistance from any Dashboard page.

The AI Agent Button is a persistent UI element (floating action button or sidebar trigger) that opens an AI interaction panel.

**Key Behaviors**:
- Always visible across all Dashboard pages
- Context-aware: knows which page/element the user is viewing
- Users can select UI targets (a paper, a date, a service) before invoking
- Opens a chat panel that supports:
  - Conversational Q&A about selected papers (via PaperLens)
  - Deep research on selected topics (via PaperLens Research Synthesizer)
  - Paper comparison across selected papers
  - Explanation of relevance scores and ranking factors
- Maintains conversation history within a session
- Can dispatch agent actions (e.g., "analyze this paper" → PaperLens, "find similar papers" → PaperScout)

### 6.5 Task Manager

**Responsibility**: Abstract background task execution, progress tracking, and logging.

The Task Manager is a backend service that wraps agent operations into trackable Background Tasks.

**Key Behaviors**:
- Creates and tracks Background Task records in Storage
- Reports progress updates (percentage, current step, message)
- Captures structured logs per task
- Supports task cancellation
- Emits real-time events for task state changes
- Handles concurrent task limits

### 6.6 Agent Dispatcher

**Responsibility**: Route Dashboard actions to the correct agent.

The Agent Dispatcher translates Dashboard user actions into agent invocations.

**Key Behaviors**:
- Maps UI actions to agent calls:
  - "Run Paper Discovery" → PaperScout agent
  - "Fill Gaps" → PaperScout Gap Scanner
  - "Sync Zotero" → SyncOrchestrator
  - "Analyze Paper" → PaperLens engine
  - "Deep Research" → PaperLens Topic Explorer
- Wraps each invocation in a Background Task for monitoring
- Passes context from UI (selected papers, date ranges, topics) to agent parameters

### 6.7 Storage Gateway

**Responsibility**: Provide read/write access to Storage Backend for Dashboard data.

The Storage Gateway handles all Dashboard queries against the shared storage.

**Key Behaviors**:
- Reads assessed papers for Paper Trend calendar
- Reads notification records for calendar status
- Reads sync logs for Profile page
- Reads/writes Background Task records
- Reads Zotero corpus and Scholar profile for service summaries

### 6.8 Real-Time Manager

**Responsibility**: Deliver live updates from backend to frontend.

The Real-Time Manager provides real-time communication for task progress and system events.

**Key Behaviors**:
- Publishes task progress events (via WebSocket or SSE)
- Notifies frontend of task completion/failure
- Supports graceful degradation to polling when WebSocket unavailable
- Manages connection lifecycle (connect, reconnect, heartbeat)

## 8. Invariants and Constraints

### 8.1 Architectural Invariants

| Invariant | Meaning | Consequence of Violation |
|-----------|---------|-------------------------|
| **DB-001**: Shared Storage | Dashboard reads/writes the same storage as agents | Data inconsistency between UI and agents |
| **DB-002**: Agent Delegation | Dashboard MUST NOT re-implement agent logic | Duplicate behavior, maintenance burden |
| **DB-003**: Task Idempotency | Triggering the same task twice MUST NOT produce duplicate side effects | Duplicate emails, corrupted state |
| **DB-004**: Progressive Enhancement | All pages MUST render with initial data load; real-time is optional | Broken UI when WebSocket unavailable |
| **DB-005**: Context Preservation | AI Agent Panel MUST receive full context of user's current UI focus | Irrelevant or generic AI responses |

### 8.2 Dependency Constraints

| Constraint | Rule |
|------------|------|
| Storage Backend | MUST be available (shared with agents) |
| PaperScout Agent | MUST be available for paper discovery and gap filling |
| PaperLens Agent | SHOULD be available for AI Agent interactions |
| LLM API | MUST be configured for AI Agent chat functionality |
| Web Server | MUST serve Dashboard frontend and API |

### 8.3 Operational Constraints

| Constraint | Description |
|------------|-------------|
| Concurrent Tasks | Maximum 3 background tasks running simultaneously |
| Task Timeout | Background tasks timeout after 10 minutes |
| Calendar Range | Paper Trend calendar supports up to 12 months of history |
| Chat History | AI Agent maintains up to 50 messages per session |
| Polling Fallback | If WebSocket unavailable, poll every 5 seconds |

## 9. Abstract Schemas

### 9.1 Background Task

Represents a trackable unit of work.

| Field | Type | Description |
|-------|------|-------------|
| `task_id` | String | Unique identifier (UUID) |
| `user_id` | String | Owner's user ID |
| `task_type` | Enum | `paper_discovery`, `gap_fill`, `sync_zotero`, `sync_scholar`, `paper_analysis`, `deep_research` |
| `status` | Enum | `queued`, `running`, `completed`, `failed`, `cancelled` |
| `progress` | Float | 0.0-1.0 completion percentage |
| `current_step` | String | Human-readable current step description |
| `parameters` | JSON | Task-specific input parameters |
| `result` | JSON | Task output (populated on completion) |
| `logs` | List[LogEntry] | Structured log entries |
| `created_at` | Timestamp | When task was created |
| `started_at` | Timestamp | When execution began |
| `completed_at` | Timestamp | When task finished |
| `error_message` | String | Error if failed |

### 9.2 Log Entry

| Field | Type | Description |
|-------|------|-------------|
| `timestamp` | Timestamp | When the log was created |
| `level` | Enum | `debug`, `info`, `warning`, `error` |
| `message` | String | Log message |
| `metadata` | JSON | Additional structured data |

### 9.3 Calendar Day Summary

Aggregated data for a single day on the Paper Trend calendar.

| Field | Type | Description |
|-------|------|-------------|
| `date` | Date | Calendar date |
| `total_papers` | Integer | Total assessed papers |
| `relevant_papers` | Integer | Papers above relevance threshold |
| `top_score` | Float | Highest relevance score |
| `avg_score` | Float | Average relevance score |
| `notification_status` | Enum | `sent`, `failed`, `missing`, `not_configured` |
| `categories` | List[String] | ArXiv categories represented |

### 9.4 Service Status

Connected service status for the Profile page.

| Field | Type | Description |
|-------|------|-------------|
| `service_name` | String | `zotero`, `google_scholar`, `email`, `llm` |
| `status` | Enum | `connected`, `disconnected`, `error`, `not_configured` |
| `last_sync_at` | Timestamp | Last successful sync |
| `sync_summary` | String | Human-readable summary (e.g., "342 papers") |
| `details` | JSON | Service-specific details |
| `error_message` | String | Error if status is `error` |

### 9.5 AI Agent Context

Context passed to the AI Agent Panel.

| Field | Type | Description |
|-------|------|-------------|
| `source_page` | String | Page where AI was invoked |
| `selected_papers` | List[String] | ArXiv IDs of selected papers |
| `selected_date_range` | DateRange | If invoked from calendar |
| `selected_service` | String | If invoked from profile page |
| `user_query` | String | User's natural language input |
| `conversation_history` | List[Message] | Previous messages in session |

## 11. Open Questions

1. **Authentication**: How should the Dashboard authenticate users? Session cookies vs. token-based auth? This is deferred to a future RFC.

2. **Multi-User**: Should the Dashboard support multiple users with separate profiles, or is it single-user? Current design assumes single-user.

3. **Offline Mode**: Should the Dashboard work offline with cached data? If so, what subset of features is available?

4. **Plugin System**: Should third-party agents be able to register Dashboard pages/panels dynamically?

5. **Mobile Layout**: Should the Dashboard provide a dedicated mobile layout, or is responsive web sufficient?

6. **AI Agent Streaming**: Should AI responses stream token-by-token, or return complete responses? Streaming provides better UX but adds complexity.

---

## 12. Conclusion

The Alithia Dashboard transforms the research assistant from a CLI-driven automation tool into an interactive, observable, and AI-augmented research companion. By reading from shared storage and delegating to existing agents, the Dashboard adds visibility and interactivity without duplicating logic.

The Background Task abstraction provides a unified monitoring layer. The Paper Trend calendar makes daily paper discovery browsable and actionable. The Profile page gives users control over their connected services. And the AI Agent Button brings PaperLens capabilities to every context, enabling researchers to ask questions, explore topics, and trigger deep research without leaving the Dashboard.

> **Alithia Dashboard: See everything, control everything, research with AI assistance — all in one place.**
